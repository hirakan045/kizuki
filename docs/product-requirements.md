## 1. プロダクトビジョンと目的

### ビジョン

> 運動しろとは言わない。ただ、運動した自分に何が起きたかは隠さず見せる。

### 目的

睡眠の質と幸福度を上げたい人に対して、**その人自身のデータで運動の効果を示す**ことで、外からの督促ではなく本人の納得によって運動が続く状態をつくる。

一般論（「運動は睡眠に良い」）は既知であり行動を変えない。変えるのは「自分の場合はこうだった」という個別の事実である、という仮説に立つ。

### スコープの但し書き

「隠さず見せる」は**扱う指標の範囲内で省略しない**という意味であり、指標を増やすことを意味しない。指標を絞ることと矛盾しない。

### 設計原則

| 原則       | 意味                                                  |
| ---------- | ----------------------------------------------------- |
| 急かさない | 促す言葉を書かない。「歩きましょう」「あと◯歩」は禁止 |
| 責めない   | 他人や理想値ではなく、過去の自分と比較する            |
| 絞る       | 指標は歩数・睡眠・幸福度の3つのみ                     |

### 主役は運動

運動（歩数）を主役とし、睡眠・幸福度をその成果として見せる。運動という投資に対するリターンを可視化する構造をとる。

## 2. ターゲットユーザーと課題・ニーズ

### プライマリペルソナ

**27歳・男性・会社員（デスクワーク中心）／Apple Watch を装着して就寝する**

- 平日は8時半出社・20時帰宅。平日に予定を入れる余地がほとんどない
- 寝つきが悪く、休日に生活リズムが崩れる。平日と休日で就寝時刻が2時間以上ずれる
- **Apple Watch を所有し、睡眠時も装着している。**ヘルスケアアプリに睡眠データは蓄積されているが、自分では開かない
- 過去に歩数計アプリと睡眠記録アプリを入れたが、いずれも2週間以内に開かなくなった
- 運動そのものは嫌いではない。学生時代は部活動、社会人になってからも断続的に運動している
- **「1日8000歩」のような目標設定と、達成できなかった日の通知に嫌悪感がある**

**このペルソナが今アプリを必要とする理由**: 運動が良いことは知っているが、忙しさの中で優先度が下がっている。「やらなければ」ではなく「やると自分はこうなる」という具体的な根拠があれば、優先度を上げられると考えている。

**Apple Watch を前提とする理由**: 睡眠の質を測るには就寝時の装着が必要。iPhone のみでは睡眠データが取得できないか、手動記録に依存することになり、本プロダクトの中核である「運動 → 睡眠」の関係を提示できない。

### セカンダリペルソナ

| 対象                     | v1での扱い                                                                                                 |
| ------------------------ | ---------------------------------------------------------------------------------------------------------- |
| iPhoneのみのユーザー     | **限定的に対応。**睡眠データが取得できない場合は歩数と幸福度のみでレポートを生成する（F-3 エラー時の仕様） |
| 既に運動習慣がある人     | 対応する。効果の確認という別の価値が成立する                                                               |
| 歩数が常時2000歩未満の人 | **v1では想定しない。**変動が小さく、行動と結果の関係を提示できない                                         |

⚠️ 以下は**開発者自身の実感に基づく仮説**であり、ユーザー調査による検証は行っていない。v1の実使用を通じて検証する。

| P-2 | 既存アプリが急かしてくる。目標歩数・ストリーク・達成率を毎日突きつけられる | 競合調査で確認済み（下記）                           |

### ニーズ

- 一般論ではなく、自分にとっての効果を知りたい
- 自分で操作できるレバーを見つけたい
- 責められずに、事実だけ知りたい
- 入力の手間が極小であってほしい

### 市場仮説のリスク

⚠️ **「促されたくない層」の規模は未検証。**

差別化の根拠が現時点では「誰もやっていない」という事実のみであり、**空白が需要の不在によるものである可能性を否定できていない。**v1はこの仮説の検証を兼ねる。

## 5. ユーザーストーリー

### US-1: 朝の記録とレポート（メイン動線）

> 朝起きてスマホを見たとき、昨日の自分がどんな一日だったかを1タップで答えるだけで、昨日の行動と今朝の結果の関係が分かるようにしたい。何をすれば自分の調子が良くなるのか知りたいから。

```
起床を検知
  ↓
通知「昨日はどんな一日でしたか。1タップで今朝のレポートが届きます。」
  ↓
開く → 幸福度を5段階で1タップ
  ↓
昨日の歩数・睡眠時間・幸福度をAIに渡す
  ↓
生成中は処理内容を表示
  ↓
レポートが表示される
```

### US-1b: 夜のうちに入力しておく

> 一日の終わりに、その日がどうだったかを記憶が新しいうちに記録しておきたい。翌朝はレポートを読むだけにしたいから。

```
就寝予定時刻の1時間前以降にアプリを開く
  ↓
「今日はどんな一日でしたか」→ 5段階で1タップ
  ↓
翌朝はレポートが生成され、読むだけで済む
```

⚠️ 夜の入力を促す通知は送らない。ユーザーが自発的に開いたときにのみ入力できる。

### US-2: 入力を忘れた日の復帰

> 数日入力を忘れてしまったとき、履歴から過去の日付を選んで後から入力できるようにしたい。一度途切れたら二度と使わなくなるのを避けたいから。

### US-3: 傾向の把握

> 何日か使ったあとに、自分の歩数と睡眠の推移を1つのグラフで見たい。日々の変化ではなく全体の傾向を知りたいから。

### US-4: 発見の提示

> アプリを開いたとき、前回より何か新しいことが分かっている状態にしてほしい。同じ数字が並ぶだけなら開く理由がないから。

### アンチストーリー（意図的に実現しない）

- 目標歩数を設定して、達成状況を教えてほしい
- 連続記録が途切れないよう通知してほしい
- 一般的な理想値と比べて自分がどうかを知りたい

いずれも「急かさない・責めない」原則に反する。

## 6. 機能要件

### F-1: HealthKit連携

| ID    | 要件                                          | 優先度 |
| ----- | --------------------------------------------- | ------ |
| F-1-1 | 歩数を統計クエリ（`cumulativeSum`）で取得する | Must   |
| F-1-2 | 睡眠時間を取得する（`sleepAnalysis`）         | Must   |
| F-1-3 | 権限リクエスト完了後にデータ取得を実行する    | Must   |
| F-1-4 | 上記2指標以外は取得しない                     | Must   |

**F-1-1の根拠**: 全サンプルを取得して単純合計すると、iPhoneとApple Watchが同じ時間帯を別々に記録しているため二重計上される（実測: 単純合計3,919歩 / 統計クエリ2,110歩 / ヘルスケアアプリ表示2,110歩）。

**F-1-3の根拠**: 認証前にデータ取得を呼ぶとクラッシュする（ライブラリ仕様）。

### F-2: 幸福度の記録

| ID    | 要件                                               | 優先度 |
| ----- | -------------------------------------------------- | ------ |
| F-2-1 | 5段階を1タップで入力できる                         | Must   |
| F-2-2 | 選択肢は数字ではなく表情/言葉＋絵文字              | Must   |
| F-2-3 | **当日分を、就寝予定時刻の1時間前から入力できる**  | Must   |
| F-2-4 | 翌朝、前日分が未入力であれば入力できる             | Must   |
| F-2-5 | 履歴画面から過去日を選んで後追い入力できる         | Must   |
| F-2-6 | 就寝予定時刻をユーザーが設定できる（初期値 23:00） | Must   |

#### 入力可能な時間帯

| 対象                               | 入力可能になる時刻                          | 質問文                         |
| ---------------------------------- | ------------------------------------------- | ------------------------------ |
| **当日分**                         | 就寝予定時刻の1時間前〜翌日の入れ替わりまで | 「今日はどんな一日でしたか」   |
| **前日分**（当日中に未入力の場合） | 翌朝、アプリ起動時                          | 「昨日はどんな一日でしたか」   |
| 過去日分                           | いつでも（履歴画面から）                    | 「◯月◯日はどんな一日でしたか」 |

**設計意図**: 一日の記憶が新しい夜のうちに入力できるほうが、回答の精度が高い。夜に入力しておけば翌朝の操作はゼロになり、レポートを読むだけで済む。

⚠️ **夜の入力を促す通知は実装しない。**アプリを開いたときに入力できるだけであり、督促は行わない（設計原則「急かさない」）。

#### 日付の帰属

- 幸福度は**評価対象の日付**に紐づける。23時に入力した当日分は、その日の日付のレコードになる
- 日付の切り替わりは 00:00（端末のローカル時刻）
- 就寝予定時刻が 00:00 以降に設定された場合も、評価対象は「その日」とする

**F-2-3・F-2-4の根拠**: 「今どんな気分か」を朝に聞くと前夜の睡眠の評価に寄り、運動との関係が測れない。一日全体を評価対象とすることで、その日の行動と結果の関係を捉えられる。

### F-3: AIレポート

| ID    | 要件                                             | 優先度 |
| ----- | ------------------------------------------------ | ------ |
| F-3-1 | **アプリ起動時、当日分が未生成であれば生成する** | Must   |
| F-3-2 | 幸福度の入力を受けてから生成する                 | Must   |
| F-3-3 | 起床検知をトリガーに、通知を送る                 | Should |
| F-3-4 | 生成中は処理内容を表示する                       | Should |
| F-3-5 | 「今日の発見」を1件含める                        | Must   |
| F-3-6 | 生成済みレポートは保存し、再生成しない           | Must   |
| F-3-7 | 日別詳細画面を開いたとき、対象日（直近30日以内）の幸福度が入力済みでレポートが未生成なら生成する | Should |

**F-3-1の設計判断**: 起床検知の実装方式は未確定であり、iOSのバックグラウンド実行はタイミングをOSに委ねるため確実性がない。Must要件を未確定事項に依存させないため、**生成のトリガーはアプリ起動とし、起床検知は通知（Should）にのみ用いる。**通知が届かなくてもユーザーが自分で開けばレポートは得られる。

**F-3-7の設計判断**: 対象を直近30日以内に限るのは、レポート生成に使う`history`（直近30日分の歩数・睡眠）がその範囲でしか同期されないため（WBS 5.3.8）。それより古い日は歩数・睡眠のコンテキストが揃わず、レポート精度が落ちる。

#### レポートの構成

| #   | 内容                               |
| --- | ---------------------------------- |
| 1   | 昨夜の睡眠（自分の平均との比較で） |
| 2   | 昨日の歩数と、睡眠・幸福度の関係   |
| 3   | 今日の発見（1件）                  |

#### 「今日の発見」の定義（F-3-5）

アプリは直近30日分の生データ（歩数・睡眠）と、直近2日分に使われた発見の種類をAIにそのまま渡す。**種類の判定と選択はAIが行う**（2026-08-14に決定。当初はアプリ側で決定論的に判定する設計だったが、実装量と将来の調整コストを踏まえてAI判断に変更）。同じ種類が3日連続で選ばれないよう、直近2日分の種類を渡して回避させる。

AIは渡された実データの範囲内の事実のみを根拠にする（存在しない数値や誇張した表現を作らない）。

| 種類                 | 成立条件                                       | 例                                                  |
| -------------------- | ---------------------------------------------- | --------------------------------------------------- |
| D-1 過去最高         | 直近30日で歩数・睡眠のいずれかが最大           | 「先月以降でいちばん歩いた日でした」                |
| D-2 平均との差       | 平均から標準偏差1つ分以上離れている            | 「いつもより1時間多く眠れていました」               |
| D-3 連動             | 直近7日で歩数と睡眠/幸福度に同方向の変化がある | 「よく歩いた日は、翌朝の調子も上がっていました」    |
| D-4 曜日の傾向       | 同一曜日のデータが3件以上ある                  | 「木曜は歩数が少なくなる傾向があります」            |
| D-5 週次の変化       | 前週・今週それぞれ7日中5日以上データがあれば、両週の平均を比較する | 「先週より平均で900歩増えています」                 |
| D-6 データ蓄積の予告 | 上記いずれも成立しない場合の**フォールバック** | 「あと3日分たまると、曜日ごとの傾向が見えてきます」 |

⚠️ D-5の閾値は当初「データ14日以上（欠損なし）」としていたが、HealthKitの欠損（Watch未装着日等）を考慮すると厳しすぎるため、**各週5日以上のデータがあれば計算可**に緩和した（2026-08-14）。

**初期状態の扱い**: 各行の成立条件が自然にデータ量のガードになる（例: D-4は同一曜日3件必要、D-5は各週5日必要）。どの条件も満たさない間はD-6が使われる。

**D-6の文言について**: 「あと◯日分たまると〜が見えてきます」という形式は、データが蓄積されつつある事実の記述であり許容される。一方「あと◯歩」のような個人の行動目標の提示（禁止表現、後述）とは区別すること。

#### プロンプトの制約

| 制約                               | 内容                                                     |
| ---------------------------------- | -------------------------------------------------------- |
| 専門用語を使わない                 | 睡眠効率、HRV、REM等の語を使わない                       |
| 促す表現を禁止                     | 下記の判定基準に従う                                     |
| 良くなっている点から書き始める     | 悪い点を省略するのではなく、記述の順序を変える           |
| 二人称。温度は持つが人格は装わない | 「心配しています」「応援しています」等の感情表明をしない |
| 各2〜3文、全体10文程度             | —                                                        |

#### 「促す表現」の判定基準

**禁止する語尾・構文**

| 分類       | 例                                                     |
| ---------- | ------------------------------------------------------ |
| 勧誘       | 〜しましょう / 〜してみませんか / 〜するといいですよ   |
| 義務・必要 | 〜が必要です / 〜すべきです / 〜したほうがいいです     |
| 目標提示   | あと◯歩 / 目標まで / 〜を目指しましょう                |
| 評価・採点 | よくできました / 頑張りましょう / 惜しかったですね     |
| 未達の指摘 | 足りていません / 不足しています / 達成できませんでした |

**許容する形**

| 分類           | 例                                                            |
| -------------- | ------------------------------------------------------------- |
| 事実の記述     | 「昨日は8,432歩でした」                                       |
| 過去形の報告   | 「よく歩いた日は、翌朝の調子が上がっていました」              |
| 傾向の提示     | 「木曜は歩数が少なくなる傾向があります」                      |
| 条件付きの観察 | 「6,000歩を超えた日は、睡眠時間が平均より長くなっていました」 |

⚠️ **判定の原則**: 主語が「あなた（が過去にどうだったか）」なら許容。主語が「あなた（がこれからどうすべきか）」なら禁止。

#### エラー時の仕様

| 状況                     | 挙動                                                           |
| ------------------------ | -------------------------------------------------------------- |
| ネットワーク未接続       | 生成を試みず、その旨を表示。幸福度の入力は保存する             |
| 生成に失敗した           | エラーを表示し、**同一画面から手動で再試行できる**ようにする   |
| 当日中に生成できなかった | 翌日以降も、その日付を選べば生成を試行できる（レコードは残る） |
| HealthKitにデータがない  | 欠損として扱い、取得できた指標のみでレポートを生成する         |

### F-4: 履歴・グラフ

| ID    | 要件                                        | 優先度 |
| ----- | ------------------------------------------- | ------ |
| F-4-1 | 日付ごとの一覧を表示する                    | Must   |
| F-4-2 | 歩数と睡眠を重ねた折れ線グラフを1つ表示する | Should |
| F-4-3 | 過去のレポートを読み返せる                  | Should |

### F-5: 通知

| ID    | 要件                               | 優先度 |
| ----- | ---------------------------------- | ------ |
| F-5-1 | 起床検知後に朝の問いかけを通知する | Should |
| F-5-2 | 通知をOFFにできる                  | Should |
| F-5-3 | 催促・リマインドの通知は実装しない | Must   |

**通知文面**

> 昨日はどんな一日でしたか。1タップで今朝のレポートが届きます。

入力を促すのではなく、受け取れるものを先に提示する。

⚠️ 通知が届かない場合でも、ユーザーがアプリを開けばレポートは生成される（F-3-1）。通知は補助的な手段であり、必須経路ではない。

| 種別                | 出す | 理由                             |
| ------------------- | ---- | -------------------------------- |
| 催促（「あと◯歩」） | ×    | ユーザーを動かそうとする押しつけ |
| 朝の問いかけ        | ○    | 行動を促していない               |
| レポート完成通知    | ○    | 情報の伝達のみ                   |

### F-6: 設定

| ID    | 要件                                     | 優先度 |
| ----- | ---------------------------------------- | ------ |
| F-6-1 | 就寝予定時刻を設定できる（初期値 23:00） | Must   |
| F-6-2 | 通知のON/OFFを切り替えられる             | Should |

⚠️ 設定項目はこの2つのみ。比較基準や目標値など、体験に関わる設定は持たない。

## 8. 受け入れ条件と優先順位

### Must

- [ ] HealthKitから歩数を統計クエリで取得できる（F-1-1）
- [ ] HealthKitから睡眠時間を取得できる（F-1-2）
- [ ] 幸福度を5段階で1タップ入力できる（F-2-1）
- [ ] 当日分を就寝予定時刻の1時間前から入力できる（F-2-3）
- [ ] 就寝予定時刻を設定できる（F-2-6）
- [ ] 過去日の後追い入力ができる（F-2-5）
- [ ] アプリ起動時に当日分のレポートが生成・表示される（F-3-1）
- [ ] レポートに「今日の発見」が1件含まれる（F-3-5）
- [ ] レポートに禁止表現が含まれていない（F-3の判定基準）
- [ ] 生成失敗時に再試行できる（F-3 エラー時の仕様）
- [ ] APIキーがアプリに埋め込まれていない（NFR-1-1）
- [ ] プライバシーポリシーが公開されている（NFR-2-1）
- [ ] 医療機器ではない旨の注意書きがある（NFR-2-3）
- [ ] App Storeの審査を通過している

### Should

- [ ] 起床検知による通知（F-3-3・F-5-1）
- [ ] 歩数と睡眠のグラフ（F-4-2）
- [ ] 生成中の処理表示（F-3-4）
- [ ] 過去レポートの閲覧（F-4-3）

### Could

- [ ] 通知のON/OFF設定（F-5-2）

### 受け入れテスト

| #     | シナリオ                                                | 期待結果                                 |
| ----- | ------------------------------------------------------- | ---------------------------------------- |
| AT-1  | HealthKit権限を許可し、歩数を取得する                   | ヘルスケアアプリの表示と一致する         |

## 9. v2以降の検討事項

### 機能拡張

| 項目                   | 内容                                                                                            |
| ---------------------- | ----------------------------------------------------------------------------------------------- |
| 比較基準の自動判定     | 全体平均／平日休日／曜日ごとを、曜日パターンから自動で切り替える。ユーザーには設定させない      |
| 運動データの拡張       | ワークアウト（workoutType）、運動時間（appleExerciseTime）。歩数に表れない運動を拾う            |
| スクリーンタイム       | Screen Time API は entitlement 申請が必要な場合があり、Expoからはネイティブモジュール自作が必要 |
| 幸福度の入力タイミング | 夜に聞く方式への変更。測定精度は上がるが入力が2回に分かれる                                     |
| ロック画面ウィジェット | インタラクティブウィジェットからの1タップ入力                                                   |
| 概念への翻訳           | 「歩数の投資利回り」のように、抽象的な数値を誰もが持つ概念に置き換える                          |
| データ共有             | 記録を他者と共有する。認証・権限管理が前提になる                                                |
| 追加指標               | 心拍、HRV など                                                                                  |
| エクスポート           | CSV等での書き出し                                                                               |

### 技術的な発展

| 項目              | 内容                                                                             |
| ----------------- | -------------------------------------------------------------------------------- |
| インフラのAWS移行 | Lambda + API Gateway。トラフィックの形（1日1回・数秒）からサーバーレスを選定     |
| CI/CD             | GitHub Actions。テスト・lint・型チェックを自動化。リリースは審査が挟まるため手動 |

### 設計方針として採用しないもの

| 項目                       | 理由                                       |
| -------------------------- | ------------------------------------------ |
| 催促・リマインド通知       | ビジョンに反する                           |
| ストリーク（連続記録日数） | 途切れた罪悪感で離脱する                   |
| 一般統計・理想値との比較   | 毎日「足りていない」と突きつける設計になる |
| 目標歩数の設定と督促       | 既存の歩数アプリが全部やっていること       |
