# 要求 — 発見（D-1〜D-6）のAI判断化（WBS 5.2 見直し）

## 背景・方針転換

当初（本ディレクトリの旧requirements.md/design.md）はアプリ側で歩数・睡眠の実データからD-1〜D-6を決定論的に判定する設計だった（PRD F-3-5の原文どおり）。

方針を転換し、**「今日の発見」の判断そのものをAI（Claude）に任せる**。アプリは直近30日分の生データ（歩数・睡眠・幸福度）をAPIにそのまま渡し、Claudeがそのデータから該当する発見を選び、レポート内で言及する。

理由：D-1〜D-6を個別に実装するより、生データを渡してAIに判断させる方が実装量が少なく、将来の発見の種類の追加・調整もプロンプト側だけで完結する。

## やりたいこと

1. `api/report.ts` のリクエスト形式を変更し、単一日の数値ではなく直近30日分の履歴配列を渡す
2. システムプロンプトに、D-1〜D-6の定義と「データに基づかない主張をしない」制約を追加する
3. 「同じ種類の発見が3日連続で選ばれない」というF-3-5の制約を維持する
   - 直近2日分の発見種類（`discoveryKind`）を`DayRecord`に保存し、プロンプトに渡して回避させる
4. PRD（F-3-5）の記述をこの方針に合わせて更新する

## 要求内容（PRD F-3-5より、判断基準は変えない）

| 種類 | 成立条件 |
| --- | --- |
| D-1 過去最高 | 直近30日で歩数・睡眠のいずれかが最大 |
| D-2 平均との差 | 平均から標準偏差1つ分以上離れている |
| D-3 連動 | 直近7日で歩数と睡眠/幸福度に同方向の変化がある |
| D-4 曜日の傾向 | 同一曜日のデータが3件以上ある |
| D-5 週次の変化 | 前週と今週の平均を比較できる（データ14日以上） |
| D-6 データ蓄積の予告 | 上記いずれも成立しない場合のフォールバック |

判断基準そのものはPRDのまま維持し、**その判定を計算式ではなくAIに委ねる**点だけが変わる。

## 受け入れ条件

- [ ] APIに直近30日分の`{ dateKey, steps, sleepMinutes }`配列を渡せる
- [ ] レポートに含まれる「発見」が、渡したデータの範囲内の事実に基づいている（存在しない数値を主張しない）
- [ ] 直近2日で使われた発見の種類がプロンプトに渡り、3日連続で同じ種類が選ばれない指示がある
- [ ] 発見の文言に禁止表現（勧誘・義務・目標提示・評価・未達の指摘）が含まれない
- [ ] データが3日未満の場合はD-6（データ蓄積の予告）に自然に倒れる（プロンプト指示で担保）

## 対象外（今回やらないこと）

- `discoveryKind`をUIに表示する機能（レポート本文にのみ反映されればよい）
- アプリからの実際のAPI呼び出し実装（WBS 5.3.2）。今回はAPI側の変更のみ
